# امنیت و threat model

این سند کنترل‌های پیاده‌سازی‌شده، فرض‌های امنیتی و ریسک‌های باقی‌مانده را
مستند می‌کند. **هیچ ادعایی درباره «۱۰۰٪ امن» وجود ندارد.** امنیت یک فرایند
عملیاتی است، نه یک ویژگی قابل پایان.

## مدل تهدید

دارایی‌های اصلی: رمزها، نشست‌ها، اسرار TOTP، کدهای بازیابی، محتوای تیکت‌ها،
یادداشت‌های داخلی، audit log، نقش‌ها و فایل SQLite.

| تهدید | کنترل اصلی | ریسک باقی‌مانده |
| --- | --- | --- |
| IDOR / دسترسی افقی | بررسی object-level در service، فیلتر requester/assignee | خطای انسانی در endpoint جدید |
| دسترسی افقی به پیام | فیلتر `visibility=INTERNAL` برای غیرکارکنان | — |
| افزایش نقش | نقش از session، ثبت‌نام همیشه `USER`، مسدودسازی ارتقا به OWNER | نقص منطقی آینده |
| سرقت نشست | کوکی HttpOnly/Secure/SameSite، هش توکن در DB، ابطال و rotation | XSS یا دستگاه آلوده |
| CSRF | double-submit cookie + بررسی Origin + SameSite=Lax | مرورگرهای قدیمی یا origin اشتباه تنظیم‌شده |
| XSS | Vue escaping؛ بدون `v-html`؛ CSP | `unsafe-inline` در CSP |
| SQL injection | Prisma parameterized؛ بدون SQL رشته‌ای | — |
| Brute force | rate limit IP و ایمیل، Argon2id، پیام عمومی | حمله توزیع‌شده و lockout ایمیل |
| Enumeration | پاسخ یکسان ثبت‌نام/فراموشی رمز، dummy password verify | اختلاف زمانی جزئی |
| Mass assignment | Zod schema و انتخاب صریح فیلدها | فیلد جدید بدون بررسی |
| آپلود مخرب | پیوست پیاده‌سازی نشده است | — |
| نشت در log | عدم log رمز/توکن؛ audit metadata پاک‌سازی | logهای زیرساخت |
| نشت realtime | roomهای مجاز و تأیید عضویت | باگ در event جدید |
| Supply chain | lockfile، بررسی دستی پکیج‌ها | بدون CI audit خودکار |
| نشت secret | env، `.gitignore`، validate در startup | دسترسی اپراتور/سیستم |
| DoS | محدودیت body، pagination، rate limit | حمله حجم بالا در لایه شبکه |

## احراز هویت

- **هش رمز:** Argon2id با `memoryCost=19456`، `timeCost=2`،
  `parallelism=1`. رمز خام هرگز ذخیره یا log نمی‌شود.
- **سیاست رمز:** حداقل ۱۲ کاراکتر، حداکثر ۱۲۸، حداقل یک حرف و یک عدد.
  بررسی رمزهای لو‌رفته (breach check) انجام نمی‌شود.
- **پاسخ یکسان:** ورود ناموفق برای ایمیل ناموجود و رمز اشتباه پیام یکسان
  دارد؛ برای ایمیل ناموجود یک hash dummy محاسبه می‌شود تا زمان پاسخ نزدیک
  بماند.
- **ثبت‌نام:** نقش از سرور `USER` تعیین می‌شود. هیچ فیلد role از کلاینت
  خوانده نمی‌شود. ایمیل تکراری پاسخ یکسان می‌گیرد.
- **تأیید ایمیل:** توکن ۳۲ بایتی تصادفی، فقط SHA-256 در دیتابیس، TTL
  ۲۴ ساعت، یک‌بارمصرف. **ورود به تأیید ایمیل وابسته نیست.**
- **ورود کارکنان:** `ADMIN` و `OWNER` فقط با یک کلید امنیتی تصادفی
  (حداقل ۳۲ کاراکتر) وارد می‌شوند. فقط `SHA-256` کلید در
  `User.staffSecretHash` ذخیره می‌شود؛ کلید خام در دیتابیس، API یا کلاینت
  ذخیره نمی‌شود. ورود با ایمیل/رمز برای این نقش‌ها رد می‌شود.
- **Bootstrap مالک:** در startup، اگر هیچ حساب `OWNER` وجود نداشته باشد،
  از `OWNER_SECRET` ساخته می‌شود. اگر مالک قدیمی بدون کلید وجود داشته
  باشد، همان حساب به کلید env متصل می‌شود. کلید موجود بازنویسی نمی‌شود و
  ساخت مالک دوم مجاز نیست. مسیر CLI `bootstrap:owner` اختیاری و
  یک‌باره است.
- **بازیابی رمز:** توکن تصادفی ۳۲ بایتی، hash در DB، TTL یک ساعت،
  یک‌بارمصرف؛ پس از reset همه نشست‌های کاربر باطل می‌شوند.

## نشست‌ها

- توکن ۳۲ بایت تصادفی؛ فقط SHA-256 در `Session.tokenHash`.
- TTL همه نشست‌ها ۱ ساعت است؛ چالش MFA ۱۵ دقیقه. نشست منقضی در سرور
  رد می‌شود و کوکی آن پاک می‌شود.
- کوکی `tm_session`: `HttpOnly`، `SameSite=Lax`، `Secure` در production،
  `Path=/`.
- `lastSeenAt` حداکثر هر ۵ دقیقه به‌روزرسانی می‌شود تا نوشتن بی‌دلیل
  SQLite کاهش یابد.
- Login جدید با توکن قبلی همان مرورگر، نشست قبلی را باطل می‌کند.
- تغییر رمز، reset رمز، تعلیق، تغییر نقش و اقدام مدیریتی نشست‌ها را باطل
  می‌کند. تغییر نقش/تعلیق سوکت‌های کاربر را هم قطع می‌کند.
- کارکنان می‌توانند نشست‌های فعال خود را ببینند و باطل کنند؛ OWNER
  نشست‌های همه کاربران را می‌بیند و با step-up باطل می‌کند.
- پس از انقضا یا ابطال، درخواست بعدی ۴۰۱ می‌گیرد.

## MFA

- TOTP با `otpauth`؛ پنجره پیش‌فرض کتابخانه استفاده می‌شود.
- secret با AES-256-GCM و `MFA_ENCRYPTION_KEY` رمز می‌شود؛ کلید ۳۲ بایتی
  base64 است.
- فعال‌سازی با اسکن QR و تأیید یک کد انجام می‌شود.
- ۱۰ کد بازیابی یک‌بارمصرف تولید می‌شود؛ فقط hash آن‌ها ذخیره و هر کد پس
  از استفاده `usedAt` می‌گیرد.
- MFA برای کاربران عادی اختیاری است؛ نشستِ چالش‌تأییدنشده `MFA_REQUIRED`
  می‌گیرد.
- کارکنان به‌جای رمز + TOTP با کلید امنیتی وارد می‌شوند و MFA اجباری
  ندارند. در صفحه تنظیمات، گزینه تغییر رمز و MFA برای آن‌ها نمایش داده
  نمی‌شود.
- step-up برای کارکنان با ورود مجدد همان کلید امنیتی و برای کاربران عادی
  با رمز + TOTP (در صورت فعال بودن) انجام می‌شود؛ پنجره آن ۱۰ دقیقه است.
  ایجاد مدیر، تغییر نقش/وضعیت و ابطال نشست دیگران به step-up نیاز دارد.

## مجوز

مجوزها در `shared/domain.ts` متمرکز و در serviceها اعمال می‌شوند. UI فقط
برای UX مخفی می‌کند. نکات کلیدی:

- `USER` فقط تیکت‌های خودش را می‌بیند؛ تیکت دیگران حتی با id حدسی قابل
  خواندن نیست.
- `USER` نمی‌تواند یادداشت داخلی بسازد یا ببیند؛ `visibility` از payload
  توسط service بررسی می‌شود.
- `ADMIN` می‌تواند صف را ببیند و تیکت‌ها را مدیریت کند، اما فقط کاربران
  عادی را مدیریت می‌کند و نمی‌تواند نقش تغییر دهد.
- `ADMIN` نمی‌تواند حساب `ADMIN`/`OWNER` دیگر را تغییر دهد.
- `OWNER` می‌تواند ADMIN بسازد و نقش USER/ADMIN را تغییر دهد. ارتقا به
  `OWNER` از API ممکن نیست و حساب OWNER از مسیر ویرایش محافظت می‌شود.
- هیچ‌کس نمی‌تواند نقش/وضعیت حساب خودش را تغییر دهد.
- پاسخ‌های ۴۰۴/۴۰۳ وجود رکوردهای غیرمجاز را افشا نمی‌کنند.

## CSRF و مرز HTTP

- همه درخواست‌های تغییردهنده به هدر `x-csrf-token` نیاز دارند که با کوکی
  `tm_csrf` مقایسه می‌شود (double-submit).
- اگر `Origin` ارسال شود، باید دقیقاً با origin `APP_URL` برابر باشد.
- کوکی CSRF عمداً `HttpOnly=false` است تا کلاینت بتواند آن را در هدر
  بفرستد؛ مقدار آن راز احراز هویت نیست.
- بدنه JSON حداکثر ۶۴KB است (هم `Content-Length` و هم اندازه واقعی).
- همه ورودی‌ها با Zod در سرور parse می‌شوند؛ اعتبارسنجی کلاینت فقط UX است.
- پاسخ خطا شامل stack trace، SQL، مسیر داخلی یا secret نیست.
- endpointهای فهرست pageSize حداکثر ۵۰ دارند.

## Rate limiting

پیاده‌سازی fixed-window در حافظه است:

- عمومی API: ۳۰۰ درخواست در دقیقه به ازای IP هش‌شده
- ورود کاربران: ۱۰ در ۱۵ دقیقه به ازای IP و ۵ در ۱۵ دقیقه به ازای ایمیل
- ورود کارکنان: ۱۰ در ۱۵ دقیقه به ازای IP و ۵ در ۱۵ دقیقه به ازای هش کلید
- ثبت‌نام: ۵ در ساعت به ازای IP
- فراموشی/بازیابی رمز: محدودیت ساعتی
- تغییر رمز: ۵ در ساعت
- reauth: ۸ در ۱۵ دقیقه
- تیکت جدید، پاسخ، به‌روزرسانی و فهرست: سقف‌های جداگانه
- رویداد socket: ۶۰ در دقیقه برای هر سوکت

این کنترل برای یک instance مؤثر است. در چند instance باید به store مشترک
منتقل شود؛ در غیر این صورت سقف‌ها بین instance‌ها تقسیم می‌شوند.

## هدرهای امنیتی

`server/middleware/00-security.ts` موارد زیر را اعمال می‌کند:

- `Content-Security-Policy`: `default-src 'self'`،
  `script-src 'self' 'unsafe-inline'` در production (در توسعه
  `'unsafe-eval'` هم دارد)، `style-src 'self' 'unsafe-inline'`،
  `img-src 'self' data: blob:`، `font-src 'self' data:`،
  `connect-src 'self'` و origin وب‌سوکت، `frame-ancestors 'none'`،
  `base-uri 'self'`، `form-action 'self'`، `object-src 'none'`
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` محدودکننده camera/microphone/geolocation/payment
- `Cross-Origin-Opener-Policy: same-origin`
- `Strict-Transport-Security` فقط در production
- `Cache-Control: no-store` برای `/api/**`
- `X-Robots-Tag: noindex, nofollow` برای مسیرهای خصوصی و API

CSP فعلی به‌دلیل inline بودن payload hydration از `unsafe-inline` استفاده
می‌کند. انتقال به nonce/hash یک بهبود آینده است و ادعا نمی‌شود انجام شده.

## Audit و logging

رویدادهای ثبت‌شده شامل:

- ورود موفق/ناموفق/مسدود، خروج، ثبت‌نام، تأیید ایمیل
- فعال/غیرفعال‌سازی MFA، تأیید و شکست MFA، reauth
- تغییر رمز، درخواست و انجام reset
- ایجاد، تغییر وضعیت/اولویت، تخصیص و پیام تیکت
- ایجاد کاربر، تغییر نقش/وضعیت، ابطال نشست
- bootstrap مالک

`writeAudit` کلیدهای حاوی password/token/secret/code/cookie/authorization
را حذف می‌کند و رشته‌های بلند را کوتاه می‌کند. IP به‌صورت HMAC/SHA-256 با
`IP_HASH_SECRET` ذخیره می‌شود، نه خام.

در production خطاهای ناشناخته فقط `INTERNAL` با پیام عمومی برمی‌گردانند و
جزئیات در `console.error` سرور می‌ماند. رمز، cookie، توکن و secret در log
نوشته نمی‌شود. در **توسعه** و بدون SMTP، متن ایمیل تأیید/بازیابی (شامل
لینک توکن) در log چاپ می‌شود تا امکان تست باشد؛ این رفتار در production
غیرفعال است.

## Secretها

- `APP_URL`، `DATABASE_URL`، `MFA_ENCRYPTION_KEY`، `IP_HASH_SECRET` در
  startup اعتبارسنجی می‌شوند؛ نبودشان باعث fail-fast می‌شود.
- `.env`، دیتابیس، backup و client تولیدشده در `.gitignore` هستند.
- `MFA_ENCRYPTION_KEY` و `IP_HASH_SECRET` باید ۳۲ بایت base64 باشند.
- `OWNER_SECRET` فقط سمت سرور است و در باندل کلاینت قرار نمی‌گیرد. پس از
  تکمیل راه‌اندازی می‌توان آن را از env حذف کرد؛ در این حالت مالک موجود
  با کلید ذخیره‌شده وارد می‌شود.
- هیچ secretی در `runtimeConfig.public` یا باندل کلاینت قرار ندارد.
- توکن‌های reset/verification فقط hash شده ذخیره می‌شوند.

## محدودیت‌ها و ریسک‌های باقی‌مانده

1. **تأیید ایمیل اجباری نیست.** حساب ثبت‌شده بدون تأیید ایمیل می‌تواند
   وارد شود. برای enforcement باید policy و تست اضافه شود.
2. **rate limit در حافظه است.** چند instance یا restart سقف‌ها را بازنشانی
   می‌کند.
3. **CSP دارای `unsafe-inline` است.** XSS سطح حمله را کاهش می‌دهد اما به
   اندازه nonce سخت‌گیرانه نیست.
4. **SQLite رمزنگاری at-rest ندارد.** امنیت فایل به permission سیستم،
   disk encryption و backup امن وابسته است.
5. **بدون بررسی breach password.** سیاست طول/ترکیب اعمال می‌شود، اما
   رمزهای لو‌رفته شناخته‌شده رد نمی‌شوند.
6. **بدون پیوست امن.** قابلیت آپلود عمداً پیاده‌سازی نشده تا سطح حمله
   فایل اضافه نشود.
7. **بدون حساب‌های چند‌دستگاهی پیشرفته.** مدیریت نشست وجود دارد، اما
   تأیید دستگاه جدید یا اعلان ورود اضافه نشده است.
8. **بدون audit tamper-evidence.** audit log در همان دیتابیس است و در برابر
   اپراتور مخرب یا حذف فایل محافظت رمزنگاری‌شده ندارد.
9. **بدون dependency scan در CI.** پکیج‌ها بررسی شده‌اند، اما `npm audit`
   خودکار در pipeline اجرا نمی‌شود.
10. **lockout ناشی از rate limit ایمیل.** مهاجم می‌تواند با تلاش مکرر،
    ورود یک ایمیل را موقتاً محدود کند. این trade-off در برابر brute force
    پذیرفته شده است.
11. **بدون multi-instance.** rate limit، سوکت و SQLite برای یک instance
    طراحی شده‌اند.

## چک‌لیست عملیاتی

- [ ] `APP_URL` روی HTTPS و دقیقاً همان origin عمومی است.
- [ ] `TRUST_PROXY=true` فقط پشت reverse proxy مورد اعتماد.
- [ ] `MFA_ENCRYPTION_KEY` و `IP_HASH_SECRET` تصادفی و ۳۲ بایتی هستند.
- [ ] `OWNER_SECRET` تصادفی و حداقل ۳۲ کاراکتری است و پس از راه‌اندازی
      از env حذف یا در secret manager نگهداری می‌شود.
- [ ] SMTP تنظیم و تحویل ایمیل تست شده است.
- [ ] فایل SQLite روی volume پایدار با permission محدود است.
- [ ] backup زمان‌بندی‌شده و restore آزمایش‌شده وجود دارد.
- [ ] TLS/HSTS و WebSocket upgrade در reverse proxy کار می‌کند.
- [ ] کلید امنیتی مالک و مدیران در جای امن نگهداری می‌شود و نشست‌های
      منقضی در سرور باطل می‌شوند.
- [ ] لاگ‌ها بدون secret و با retention مناسب پیکربندی شده‌اند.
- [ ] پس از تغییر نقش، رمز یا تعلیق، نشست‌ها باطل می‌شوند (تست شده).
- [ ] dependency audit و patch دوره‌ای انجام می‌شود.
